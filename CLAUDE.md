# Auti: notes for Claude Code

Auti is a coordinator for a small company. On a schedule it reads the company's state from Postgres, asks Claude for a brief through one forced tool call, and writes the brief back. The owner approves anything it proposes.

- **Deploying for the first time:** follow `DEPLOY.md` step by step.
- **Running on a VPS later:** see README.md and `deploy/`.

## Commands

```bash
npm ci
npm test                 # PGlite (in-process Postgres) + a fake brain; no API key needed
npm run check:private    # must pass before every commit and push
npm run migrate          # apply db/*.sql to DATABASE_URL (idempotent)
npm run seed             # load seed/private.sql once (never committed)
npm run nightly          # one real run (needs ANTHROPIC_API_KEY)
npm run brief            # print the latest brief
```

## Layout

- `db/`: numbered migrations, applied in order and tracked in `schema_migrations`. Add a new file for any change; never edit an applied one.
- `src/coordinator.js`: one run, which writes initiatives and journal lines in one transaction.
- `src/projects.js`: the project companion (intake, brief, milestones, check-ins, health). `src/verify.js`: the free checks on a lead's site, email and DNS, and the contact email on its own website. `src/accounts.js`: collections and renewals drafts. `src/reports.js`: weekly and monthly reports.
- `src/pipeline.js`: the lead playbook (stages, rhythm, the three message styles and which one leads). `src/replies.js`: reads what leads answered in the CRM inbox before the drafts are written. `src/bounces.js`: the bounce notices among them, and the autosend pause. `src/audit.js`: the lead audits (what a lead uses online, the gaps, which product fixes each, the note in the CRM).
- `src/learning.js`: what Auti learns from every piece of its work (signals, the nightly study, lessons per agent, the owner's rules).
- `src/prompt.js`: the tool schema and the prompts. Standing instructions live in the `coordinator_config` table, not in code.
- `.github/workflows/`: `ci.yml` (tests + privacy gate) and `coordinator.yml` (scheduled runs).

## Rules

- The repo is public. Company data lives only in `seed/private.sql` and the database. Never commit it, and never print brief content in CI logs (`JARVIS_QUIET`).
- Never read out, log or commit secrets: `.env`, API keys, connection strings.
- Initiatives created by the coordinator stay `awaiting_approval`. Don't remove the `CHECK` constraint or let the coordinator approve anything.
- Automatic steps live in `src/autonomy.js`: each kind is validated in code, logged in `coordinator_action` and undoable. Only add a kind that is internal and reversible; anything the coordinator itself thinks of that contacts a client, sends a document or spends money stays a proposal.
- The chat is different: the owner is talking to Auti, so what they ask for runs (`OWNER_ACTIONS` in `src/crm.js`: CRM changes, email, WhatsApp, inbox replies, scheduling), each written in the journal. The scheduled runs never call those.
- Two owner switches (coordinator_config, Agents tab): `leads_to_crm` (on) puts leads with a business email into the CRM and the outreach queue; `outreach_autosend` (off until the owner turns it on) emails outreach touches to CRM prospects without review, on working days in office hours, at most five a day per new business (`outreach_per_day` x 5, never over `AUTOSEND_MAX` 50), never after a reply, and it switches itself off on bounces (see Bounces). `outreach_per_day` is the pace of new sequences (`nextSlot` counts only sequences still waiting for their first touch), set on the Agents tab. Follow-ups to existing clients are always drafts.
- A lead without an email gets one looked up on its own website (`findContactEmail` in `src/verify.js`). That means its own domain or the free address the site shows, role addresses first, and never another site's address, a no-reply or an image name. It happens when the lead is saved, and for leads already waiting at most 12 a night, once each (`findMissingEmails` in `src/leads.js`, before the search). A found address joins `contact_route`, where leadsToCrm reads it, and the search is kept in `checks.email_search`. A lead with none found stays on the Leads tab but doesn't count toward the 30 that pause the search (`waitingLeads`). Logs show counts only, never an address. Tests use a fake fetch and `.example` domains. Test: `test/leads.test.js`.
- Lead audits (`src/audit.js`, `node src/run.js audit` each night after the leads agent; the owner's switch `lead_audit`, on, which Rex asked for on 2026-11-09). The free facts come from the lead's own website only (`auditSite` in `src/verify.js`: the home page and its first contact page, Google's PageSpeed when it answers; names of tools and counts, never an address, a number or a person), then at most 3 searches on the cheaper model. `cleanAudit` keeps our products only and strips links and addresses from the text (the pages used stay in `sources`); an audit with `identified: false` gets no note. `writeAuditNotes` adds the latest audit once as a note on the lead's CRM client (`POST /clients/:id/notes`): it reads the client's notes first, so a note the CRM saved before a timeout is never added twice; a 404 is never tried again and a 403 stops the night's notes. Audits only research and write that note; they never contact anyone. A lead is audited again after `REAUDIT_DAYS` (120), a failed one after 7 days, and a run starts no audit after 12 minutes. The message writers read the latest audit as data (`AUDIT_FOR_CLIENT` in clientsDue). Reads and writes that need migration 025 check `auditReady` first. Logs show counts only. Tests use a fake fetch, researcher and CRM with `.example` domains. Test: `test/audit.test.js`.
- Lead playbook (`src/pipeline.js`): every message to a lead is drafted in three styles and ends with a choice of two next steps. Answers read from the CRM inbox (`src/replies.js`) are always drafts, never sent on their own, and only when the lead is waiting for us; a no or an unsubscribe makes the lead lost and nothing more is drafted. Stage moves go through `moveStage` (automatic ones only go forward; the owner's go anywhere) and each is a row in `lead_stage_event`. Test: `test/pipeline.test.js`.
- Bounces (`src/bounces.js`, migration 026; Rex picked it on 2026-11-10). `bounceOf` tells a delivery-failure notice from a person's message by the sender (postmaster, mailer-daemon, Exchange's own) or the subject, and its kind from the enhanced code and words before the copy of our message: address, refused, full, blocked (our own mail held back) or delay (ignored). readReplies sets notices apart, filed as ours or as theirs: they never count as an answer, never reach the model, and are recorded (`email_bounce`, once per CRM message id) before the model is called; `readStrayNotices` reads a mail server's own conversation and matches the address it names to a client's CRM email in the same list. A bounce marks the email `outcome = 'bounced'`; for a lead whose address failed, `outreach_ended = 'bounced'` and its waiting email drafts are dropped by Auti. `hardBounced` (kind address, 180 days) makes `checkClientEmail` (given `db`) and leadsToCrm refuse the address. `checkPause` switches `outreach_autosend` off (`updated_by = 'auti'`, one journal line) at `PAUSE_AT` 3 bounces that are at least `PAUSE_RATE` 3% of the emails sent since the owner last switched it on (seven days at most), or at once on one blocked notice; autoSendOutreach checks it before sending anything. Learning and styleStats leave bounced emails out. Reads and writes check `bounceReady` first. Logs show counts only. Test: `test/bounces.test.js`.
- Email addresses are checked before sending (`src/emailcheck.js`: syntax, reserved and throwaway domains, MX with the A/AAAA fallback; a temporary DNS failure is `valid: null`, never invalid). `checkClientEmail` in `src/crm.js` asks the CRM's own check first (`/clients/:id/email-check`) and falls back to it. crm_send_email, leadsToCrm and autoSendOutreach never send to an address that is definitely invalid (outreach ends as `bad_email`). Tests pass a fake resolver; never a real domain.
- Sending a draft from the CRM (Approvals tab, chat) goes through `sendFollowUpViaCrm` in `src/crm.js`: email, or WhatsApp through `/conversations/start` then `/conversations/:id/reply`. Never a wa.me link for a client in the CRM.
- CRM calls (`crmClient` in `src/crm.js`): 25 s per request (`CRM_TIMEOUT_MS`). Reads are retried on network failures (300 ms, 1 s); a POST/PATCH/PUT only once, and only when the failure shows it never reached the CRM (refused, DNS, connect timeout, stale socket). Never retry a change after a timeout or an HTTP error: a client must not get a message twice. Clients Auti creates carry `tags: ['auti', ...]` and `source: 'Auti'` (leads agent: `AUTI_LEADS`). Test: `test/reliability.test.js`.
- Learning (`src/learning.js`, `node src/run.js learn` each night before the coordinator): `decideFollowUp` keeps what Auti wrote (`draft_subject`, `draft_body`, `draft_style`) and why a draft was dropped (`drop_reason`; only `dropped_by = 'owner'` counts against a draft); plans and CRM changes keep their `drop_reason`. The study turns new signals into at most `MAX_LEARNED` lessons per scope in `agent_lesson`, retires at most 3 at once, never changes an owner rule or a pinned lesson, and never re-learns one the owner removed. Every agent reads `lessonsFor(scope)` after its rules and the standing instructions: lessons are advice and never loosen a rule (drafts still wait, nothing is approved by Auti). Text from clients and leads reaches the study as data only. Writes that need migration 024 check `learningReady` first, so the dashboard works before the run that applies it. Test: `test/learning.test.js`.
- Keep the tests green, and add a test with every behaviour change.
